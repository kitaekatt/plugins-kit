Skills-kit pytest suite for schema validation, audit behavior, discovery and coverage scripts, and the golden corpus.

This is the pytest suite for the skills-kit plugin. It pins the YAML schema floors for every skill type, the audit, classify, and tag passes, the discovery and coverage scripts, and a corpus of fixture trees with expected verdicts. The files group by what they pin rather than by the module under test: one file per schema feature, one per audit behavior, one per discovery script. A recurring pattern is floor-and-mutate: a shared minimum fixture, one field broken at a time, and a validation call that must name the broken field. Some suites drive the plugin's JavaScript detect lanes under Node to reach behavior a text pin cannot, and the corpus replays its fixtures through the same audit entry points.

Where to start

Open conftest.py first. Its floor fixtures and the make_invalid mutator are the pattern most of the suite builds on, and its header explains the environment guard that stops a plugin script from re-executing the pytest process at import time.

Routes

  • Catch schema drift: take a floor fixture from conftest.py, break one field with the mutator, and run the matching schema file, test_schemas.py for the original pattern or test_capability_skill_schema.py for the newest type.
  • Trace a detect-lane change: the text pins in test_coverage_workflow_contract.py name the contract, and test_coverage_batching.py executes the same lane under Node when behavior rather than wording is at stake.
  • Replay the corpus: the fixture trees under golden_corpus/fixtures/ pair by ID with the verdicts under golden_corpus/expected/, and golden_corpus/test_golden_corpus.py drives the runner end to end.

Shared fixtures

  • conftest.py -- the minimum-floor fixture for each skill type plus the deep-copy mutator. Open it when a new schema field needs a test or when collection dies before any test runs.

Schema floors and drift

  • test_schemas.py -- the original floor-and-mutate suite; the reference for how the others read.
  • test_capability_skill_schema.py -- the capability type's floor, its forbidden keys, and the optional add-ons like members and subdomain config.
  • test_anti_patterns.py -- where the optional anti_patterns field is legal and what shape each entry must carry.
  • test_claude_md_floor.py -- the insights/conventions union floor: a conventions-only block passes, an empty block does not.
  • test_asset_dependencies.py -- the asset_dependencies record and the audit check that resolves every declared path.
  • The remaining schema and engine tests are one file per feature; match the field under test to the filename.

Audit and document parsing

  • test_classify.py -- classify verdicts across the YAML-contract, frontmatter-disagreement, and heuristic paths.
  • test_audit_frontmatter_full_parse.py -- folded and quoted frontmatter must parse to full text; a light regex read lies about length and directive form.
  • test_audit_fence_stripping.py -- type-specific heuristics ignore fenced code, so steps and tables inside a fence do not count.
  • test_detect_schema_prompt_conformance.py -- every required schema field must be named in the prompt text the model actually sees.
  • A dozen more files pin thresholds, rule IDs, verdict vocabulary, the parse-error paths, and tag behavior; open them by the audit row they guard.

Discovery and coverage scripts

  • test_discover.py -- root-versus-child classification of the files the discover script finds, the project-boundary walk, and noise-directory reporting.
  • test_coverage_discover.py -- the non-recursive coverage subject and the ambient ancestor chain, including vendored and symlinked trees.
  • test_composition_discover.py -- the composition subject, a code leaf plus every ancestor, and why that set is wider than the coverage one.
  • test_coverage_subjects.py -- the subjects-file builder and the verifier gate; every check has a test that trips it and names the offending subject.
  • The shared walk helpers and the remaining discovery scripts get the same one-file-per-behavior treatment.

md-domain lane contracts

  • test_coverage_workflow_contract.py -- the text-level pins: verdict vocabulary, the model pin, the missing-criteria guard, and the report-only posture.
  • test_coverage_batching.py -- the exception to the text-pin rule; it executes the coverage detect lane under a Node harness and checks responses against the lane's own schemas.
  • test_ancestor_exception_awareness.py -- the exception carve-out across three detect lanes and the shared audit prose, with the taxonomy IDs left un-unified on purpose.
  • test_domain_members_resolve.py -- the on-disk roster matches the dispatch table: four surviving skills, the registered lanes, every bound path resolved.
  • The remaining detect-lane and standards-doc pins follow the same read-and-pin-its-phrasing approach; the filename names the lane.

The golden corpus

  • golden_corpus/README.md -- the corpus guide: what each case exercises and how to replay it.
  • golden_corpus/corpus_runner.py -- replays the fixtures through the audit entry points and compares them with the expected verdicts.
  • golden_corpus/test_golden_corpus.py -- the pytest entry point for the replay.
  • golden_corpus/fixtures/ -- the input trees, one directory per case: the c-prefixed dimension cases, the s-prefixed skill cases, plus the references and project-doc cases.
  • golden_corpus/expected/ and golden_corpus/expected-lanes/ -- the expected verdicts, named per fixture ID; the lanes files hold one expectation per audit lane.
