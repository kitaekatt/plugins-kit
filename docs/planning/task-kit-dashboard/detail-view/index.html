Task detail view: mockups

4 concepts

Opening a task you are working on shows mostly controls for launching agents, and little that connects the task to the work. The rulings: orient first; the orientation text is a generated summary that records the commit and date it was made from; and there are different views into a task, each with the information and controls that fit it. These four static mockups explore that. They use the visual language of the served dashboard and a real task's content, shortened and paraphrased.

What all four share
  • A generated summary at the top, with its as-of commit, time, model and whether it is still current.
  • Goal and next steps from CLAUDE.md, progress from plan.md, latest commits, outputs and dependencies: all in the task folder or git, none shown today.
  • Run and authoring controls move out of the default view; each item shows only the action its state allows.
  • Bookkeeping log lines are hidden by default (22 of the sample task's 25 dated log lines are "update: refresh (no field edits)").
  • "Resolve in Claude Code" becomes "Open in Claude Code", because it is the way back into any task, not only a blocked one.

In each mockup, tick "Mark data not served today" to outline every element that needs data the dashboard does not serve yet. Theme buttons switch light and dark; every page also works at phone width.

Concepts
Concept A

Views

The task gets a page of its own with four views. Overview orients you and carries no run controls; Items is the stage map with item actions; Run holds the hold state, run options, Queue all and past runs; History merges progress, commits, runs and the log. Each view shows only its own information and controls: the most literal reading of "different views into a task".

Strengths
  • Cleanest separation of orient, act and run.
  • Deep-linkable (a URL per task and view); each view can grow without crowding the others.
Costs
  • Leaves the list: one more navigation step, and you lose sight of the other tasks.
  • A live run or a waiting decision is hidden behind a tab unless the header markers carry it.

Judge: Do you want a page per task, and are Overview / Items / Run / History the right four views?

Concept B

Brief

Keeps today's inline expansion but makes it read like a one-page brief: summary, goal, open items each with the one action its state allows, recent progress, and a fact rail (status, working sessions, latest commits, outputs). Run work and the log fold into collapsed sections at the bottom.

Strengths
  • Smallest change from today; one scroll, no mode to learn.
  • Easy to scan; the rail answers "who, what changed, where are the files".
Costs
  • Long; the same layout whatever the task's situation.
  • Run work is two clicks away for tasks you mainly run unattended.

Judge: Is one fixed reading order enough, and are the rail facts the right ones?

Concept C

Situation card

The top of the expansion is a card chosen by what is going on: a session is working it (since when, the commits since then, a resume command), it waits on you (each decision with its question, defaults and actions), or you are picking it back up (where it stands, the hand-off note, the start command). The rest folds into a facts strip and sections.

Strengths
  • The first thing you see is what you would act on.
  • Connects the task to the session and commits that are working it, which is the gap you named.
Costs
  • If the rule that picks the card is wrong, the card misleads.
  • Needs the most new data (hand-off note, current item, commits since registration); layout shifts between visits.

Judge: Are working / waiting / returning the right situations, and is the precedence order right?

Concept D

Timeline

A "now" strip (summary, next, waiting and working) and then one timeline that merges progress, code and task-record commits, sessions, runs and the log. Pick an item on the left to filter the timeline to it and get that item's actions.

Strengths
  • Best at "what was I doing, what happened since".
  • Commits sit beside progress, so the task links to the code.
Costs
  • Weakest at "what is the goal"; it is a feed.
  • Needs a join across two repositories and the run store; event-to-item links are a heuristic.

Judge: Is history-first the orientation you want when you open a task you are working on?
