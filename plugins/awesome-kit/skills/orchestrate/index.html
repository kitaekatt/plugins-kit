Orchestrate skill: delegation through background agents, shipped default policy, and scripts that render the resolved policy and launch work units

This is the orchestrate skill, a technique skill that takes on the orchestrator role whenever it is invoked and runs the work through background agents. Its working rule: the main context keeps coordination, judgment, verification, and synthesis, and every implementation unit, even a small or unsplittable one, is delegated. Two kinds of material live here, and the split drives the shape of the directory. One is durable prose stating the delegation contract; the other is variable policy that is configuration, rendered for the machine running it, never remembered. That policy resolves through four layers, shipped defaults first with machine, user, and project overrides merged on top and later layers winning.

Where to start

Start with SKILL.md: it states the one-level autonomy contract, the edges that stop the orchestrator instead of letting it decide, and the rule that routing is done against the rendered policy, not memory. Open scripts/orchestration_guidance.py second, because every routing decision is made against the block that script prints.

Routes

  • Render the policy before planning. SKILL.md step 2 runs scripts/orchestration_guidance.py with the --self flag, once per orchestration and before any decomposition, because the rendered block governs the plan itself.
  • Trace a resolved value through the layers. defaults/orchestration.yaml says to inspect the layering with scripts/orchestration_guidance.py: --explain reports which layer set each value, and --paths reports where each layer was read from.
  • Launch a Codex unit. scripts/dispatch.py re-executes the process through scripts/bootstrap_guard.py, resolves the requested model entry id, checks the content-addressed cache, and invokes codex exec.

The delegation contract

SKILL.md is the full definition of the technique skill: the one-level autonomy contract and the four edges that stop the orchestrator instead of letting it decide, the do-not-delegate list, and the step procedure from policy render through dispatch to join. Open it to change how the orchestrator behaves or to re-read what a step expects. The reference set its policy block points at, the configuration schema, controlled vocabulary, backend dispatch notes, and routing tuning, has its own page; the references card routes there.

The shipped defaults

defaults/orchestration.yaml is the default layer of the orchestration policy, the only one that ships with the plugin. It holds the resolution semantics, the controlled lexicon the routing rows are stated in, the ordered routing rows with their model menus, and the machine half recording backends and capacity. It is not edited in place; a plugin update replaces it, so tuning goes into sparse override files at the machine, user, and project layers that merge on top, record lists merging by id and disabled records dropping out.

Rendering the resolved policy

scripts/orchestration_guidance.py merges the four layers, detects which dispatch backends actually exist on this machine, probes usage capacity, and prints the resolved policy as a markdown block that routing is done against. A backend or model the renderer cannot verify here drops out of the output, so absence from the render is not evidence a tool is missing. Open it to re-render the policy, and run it with --explain when a routing row, model entry, or capacity figure looks wrong and you need to see which layer set it.

Launching work units

scripts/dispatch.py is the only sanctioned launcher for a Codex unit. It re-executes the process under the plugin's provisioned venv, resolves the requested model entry id against the registry with no default to fall back on, keeps a content-addressed dispatch cache so an unchanged unit is a cache hit, and invokes codex exec through the shared argv builder. Open it when a Codex dispatch misbehaves; --print-only shows what a launch would run without running it, and --list shows the cache.

The venv guard

scripts/bootstrap_guard.py is the stdlib-only guard the other two scripts import first. It detects whether the bootstrap plugin provisioned this plugin's virtualenv, re-executes the process under that venv before the imports that need it, and exits with an actionable message when provisioning has not happened. Open it when a script reports the plugin as not provisioned, or when the canonical copy here needs to stay in sync with the vendored copies in other plugins.
