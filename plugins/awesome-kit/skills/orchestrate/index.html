The orchestrate skill that delegates implementation units to background agents: its procedure, shipped routing policy, the per-machine policy renderer, and the dispatch and configuration references

This skill is the awesome-kit plugin's procedure for delegating implementation work to background agents while the main agent retains coordination, judgment, and synthesis. Its organizing principle is that routing policy is configuration rendered at runtime: a script merges four layers of YAML (shipped, machine, user, project) and probes for available dispatch backends, producing a per-invocation decision tree that tells the orchestrator which model to dispatch each unit to. The territory splits into the procedure document, the shipped policy, per-backend dispatch references, a controlled vocabulary with a tuning guide, and four scripts that render policy and execute dispatches.

Where to start

Open the procedure document to recover the seven-step flow and the four autonomy edges that stop the orchestrator. The shipped policy file beside it is the default every render starts from; the plugins/awesome-kit/skills/orchestrate/references/configuration.md explains how to override it per user or project.

If you are here to change routing frequency rather than run the procedure, go straight to plugins/awesome-kit/skills/orchestrate/references/tuning-selection.md and the lexicon.

Routes

  • Render policy and dispatch a unit
    1. Run the policy renderer inline at step 2: plugins/awesome-kit/skills/orchestrate/scripts/orchestration_guidance.py with your endpoint alias, then run the presence probe.
    2. Read the rendered decision tree: shape tests, routing rows, backend mechanics, and capacity.
    3. Match each decomposed unit to the first routing row whose shape terms all apply; announce the choice.
    4. Launch via the Codex dispatcher ( plugins/awesome-kit/skills/orchestrate/scripts/dispatch.py), the Agent tool, or the OpenCode CLI per the rendered backend record.
  • Override the routing policy
    1. Edit the user-layer or project-layer plugins/awesome-kit/skills/orchestrate/defaults/orchestration.yaml with sparse overrides: change only the keys you want to alter.
    2. Re-render with the --explain flag to confirm the four-layer merge, backend detection, and routing rows.
  • Tune a routing row's frequency
    1. Collect a sample of announcement lines over several invocations; note which rows fire and how often.
    2. Adjust a lexicon test, a shape term, or row order in your override; the plugins/awesome-kit/skills/orchestrate/references/tuning-selection.md ranks knobs by travel per risk.
    3. Re-render and compare the new announcement distribution against the sample.

The procedure and shipped policy

  • plugins/awesome-kit/skills/orchestrate/SKILL.md -- the seven-step orchestration procedure, the autonomy model, the do-not-delegate boundaries, and the policy-render block; open it to recover the full workflow and the four edges that stop the orchestrator.
  • plugins/awesome-kit/skills/orchestrate/defaults/orchestration.yaml -- the shipped default: resolution semantics, lexicon entries, shape tests including the parallel-development razor, ordered routing rows, backend records, and capacity fields; the layer every override merges into.

Dispatch mechanics

  • plugins/awesome-kit/skills/orchestrate/references/codex-dispatch.md -- Codex CLI flags, the one invocation shape, sandbox behavior, exit-code traps, Windows path casing, and custom-provider wiring; load it when composing a Codex launch after the rendered policy has chosen that backend.
  • plugins/awesome-kit/skills/orchestrate/references/opencode-dispatch.md -- OpenCode CLI flags, the one-shot invocation, model-entry resolution through llm-kit, and the absence of a sandbox; load it when composing an OpenCode launch.

Configuration and vocabulary

  • plugins/awesome-kit/skills/orchestrate/references/configuration.md -- the full schema for all four layers, merge rules, routing row fields, backend records, capability keys, and the explain and paths flags; open it when adding or changing an override.
  • plugins/awesome-kit/skills/orchestrate/references/lexicon.md -- the controlled vocabulary with tests, glosses, and anti-terms; open it when a shape term is firing differently than expected or when composing an announcement line.
  • plugins/awesome-kit/skills/orchestrate/references/tuning-selection.md -- which configuration keys change a routing row's match frequency, ranked by travel per risk, with worked examples; open it when a row fires too often or too rarely.

Rationale

plugins/awesome-kit/skills/orchestrate/references/why-delegate.md carries the token-economics behind delegation and a catalogue of nine named anti-patterns with their alternatives. Open it to understand why the procedure is shaped as it is; nothing in it is needed to execute a dispatch.

Scripts

  • plugins/awesome-kit/skills/orchestrate/scripts/orchestration_guidance.py -- the policy renderer: merges the four layers, detects backends, resolves model entries through llm-kit, applies consent scopes, and prints the decision tree; run it inline at step 2, once per orchestration.
  • plugins/awesome-kit/skills/orchestrate/scripts/dispatch.py -- the Codex dispatcher with a content-addressed cache keyed on model, effort, sandbox, cwd, and brief hash; resolves the entry, builds argv through the shared llm-kit builder, and records meta.
  • plugins/awesome-kit/skills/orchestrate/scripts/bootstrap_guard.py -- vendored stdlib-only guard: detects whether bootstrap provisioned the plugin venv and re-execs into it; imported by the other scripts before their shared-lib imports.
  • plugins/awesome-kit/skills/orchestrate/scripts/presence_probe.py -- probes for presence-kit's waiting rule; prints one to three lines when the sibling plugin is installed and current, silent otherwise; run once alongside the policy render at step 2.
