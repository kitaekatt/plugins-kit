The task-system implementation: task lifecycle and discovery, the model-answers engine, programmatic export, and manager operations.

This package is the implementation behind the task skill's command line, organized by the job each module does: find and project tasks, change a task's state, run the model-answers engine over the question catalog, and serve JSON to consumers. The read path is pure: every listing, export and answer pass projects the task folders as they sit on disk, so writing an answer never changes the fingerprint of the inputs that produced it. The write path is its opposite: mutations serialize per repository, compare a content revision, and validate before a byte lands. Answer records carry a machine fingerprint, so two machines answering one task write different files and merge cleanly.

Where to start

Open plugins/task-kit/skills/task/scripts/task_system/discovery.py first: the enumeration that list, review, export and the answers engine all project over, so its readings explain most surprising listings. For the answers pipeline, open plugins/task-kit/skills/task/scripts/task_system/answer_engine.py instead: its prepare, answer, commit pass is the map of the whole flow.

Routes

  • Read the task list
    1. plugins/task-kit/skills/task/scripts/task_system/discovery.py enumerates and classifies every task in scope
    2. plugins/task-kit/skills/task/scripts/task_system/listing.py projects each into a view with summary state, sessions and answers
  • Run an answers pass
    1. plugins/task-kit/skills/task/scripts/task_system/answers_cli.py task-kit answers refresh; one pass per repository
    2. plugins/task-kit/skills/task/scripts/task_system/answer_engine.py prepare, answer, commit; no lock is held across a model call
    3. plugins/task-kit/skills/task/scripts/task_system/answer_chain.py one question, validated, grounding-checked
    4. plugins/task-kit/skills/task/scripts/task_system/answer_store.py the record file this machine writes
  • Export facts to a consumer
    1. plugins/task-kit/skills/task/scripts/task_system/export_cli.py task-kit export; the envelope, exit codes, lock-free git
    2. plugins/task-kit/skills/task/scripts/task_system/export.py the task-facts payload, built through the domain readers
  • Move a task's state
    1. plugins/task-kit/skills/task/scripts/task_system/init.py scaffolds a folder that must validate active, else it removes itself
    2. plugins/task-kit/skills/task/scripts/task_system/authoring.py the plan.md item edit, proven in memory before a write
    3. plugins/task-kit/skills/task/scripts/task_system/location_ops.py archive or delete; commit-first where git can record
  • Drive it from a manager
    1. plugins/task-kit/skills/task/scripts/task_system/manage.py the negotiated operations: create, update, item verbs, dismiss
    2. plugins/task-kit/skills/task/scripts/task_system/authoring.py the pure edit an item add runs through

Finding and reading tasks

  • plugins/task-kit/skills/task/scripts/task_system/discovery.py The section-8 algorithm: folder crawl plus embedded task refs, deduped and classified. Open it when a listing surprises you; its docstring records every reading it chose.
  • plugins/task-kit/skills/task/scripts/task_system/listing.py The projection behind the list and review verbs: summary state, sessions and answers per task.
  • It leans on the companion readers in the file tree: validation, schemas, items, questions, VCS.

Changing task state

  • plugins/task-kit/skills/task/scripts/task_system/init.py The init verb: scaffolds the folder, seeds the record, validates. A failing scaffold removes itself.
  • plugins/task-kit/skills/task/scripts/task_system/authoring.py Pure task authoring: input rules and the plan.md item edit, proven in memory first.
  • plugins/task-kit/skills/task/scripts/task_system/location_ops.py archive and delete: commit-first where git can record, parking where it cannot. Its docstring is the disposition manual.
  • State changes share the mutation internals every write verb runs through.

The model-answers engine

  • plugins/task-kit/skills/task/scripts/task_system/answer_engine.py One pass per repository: prepare, answer, commit. No lock across a model call; a stop never discards paid work.
  • plugins/task-kit/skills/task/scripts/task_system/answer_chain.py The model answerer: cost-class phases, persistent re-selection, strict validation with grounding checks.
  • plugins/task-kit/skills/task/scripts/task_system/answer_store.py The record store: layout, ownership by fingerprint, and the rule that chooses among a question's records.
  • plugins/task-kit/skills/task/scripts/task_system/answer_scripts.py Deterministic script answers, computed on read and never stored, plus the one-git-log repository history.
  • plugins/task-kit/skills/task/scripts/task_system/answers_cli.py The answers command line: refresh, status, prune, protocols; one JSON document per outcome.
  • plugins/task-kit/skills/task/scripts/task_system/answers_config.py Shipped defaults under the skill, replaced key by key by the fleet file.
  • plugins/task-kit/skills/task/scripts/task_system/answers_types.py The frozen data types the pipeline codes against; changes are reported, never made in passing.
  • Beside these: the catalog loader, the input readers that fingerprint a question's inputs, and the publisher.

Machine and session identity

  • plugins/task-kit/skills/task/scripts/task_system/machine.py This machine's host id, fingerprint and OS flavor; an unreadable id is an error, not a guess.
  • plugins/task-kit/skills/task/scripts/task_system/harness.py Which Claude Code session is calling: session id, verified process, transcript. A PID must be a live ancestor.
  • plugins/task-kit/skills/task/scripts/task_system/legacy_stop.py Stops a dashboard server an earlier task-kit started, identity-checked by PID and creation time.
  • The session store, its configuration, and the lock and stamp helpers sit beside these.

Programmatic surfaces

  • plugins/task-kit/skills/task/scripts/task_system/export.py Task facts as JSON for another program, built through the domain readers. Views and filters are the consumer's.
  • plugins/task-kit/skills/task/scripts/task_system/export_cli.py The export command line: envelope, exit codes, and lock-free git so even git status writes nothing.
  • plugins/task-kit/skills/task/scripts/task_system/manage.py Negotiated operations for a manager; a partial write names the files it touched.

Package plumbing

  • plugins/task-kit/skills/task/scripts/task_system/__init__.py The package docstring: where the spec it builds to lives, and what each step shipped.
  • plugins/task-kit/skills/task/scripts/task_system/datadir.py Resolves the plugin's data directory from the venv running it; machine-scoped state lives under it, and a foreign venv is refused.
