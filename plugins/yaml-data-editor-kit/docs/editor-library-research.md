# Browser library options for the YAML data editor -- decision menu

Research only. No installs, no code, no repo writes. Five research passes were run in parallel (data grids, schema-driven forms, tree/JSON structured editors, text/code editors, comment-anchoring), each required to fetch and confirm a live public demo before citing it. Verification status is reported per candidate -- several demos could not be confirmed interactively because they are client-rendered SPAs that the fetch tool cannot execute JavaScript for; those are flagged explicitly rather than asserted.

Grounding used: `yaml-data-editor-kit/docs/dialect.md` (the custom `type`/`view`/`source` dialect -- not JSON Schema -- with `variants:` discriminated unions, `extensible:` sparse inheritance, typed `ref:`, `shape_from:`, fixed-length arrays), `yaml-data-editor-kit/CLAUDE.md` (the file-seam architecture: Python dispatcher and browser editor never share a process, only files), and the wiki generator's `CLAUDE.md`, whose UX rules are inherited acceptance criteria, quoted verbatim where load-bearing.

Ruled constraints quoted from the wiki generator (not preferences):

> A HORIZONTAL SCROLLBAR IS A UX FAILURE. There is no case where one is the right answer.

> A card sizes itself to its content, up to a maximum width and height. It is not a fixed box that content scrolls inside.

> A detail card MUST show every piece of information its entity's summary shows.

> Hover the NAME to raise a card. Click the NAME to pin it. ... Only the name raises a card.

> NO INFORMATION IS DUPLICATED ANYWHERE.

These matter directly: hover-only interaction and horizontal-scroll table degradation are both disqualifying behaviors for a mobile target, not style notes.

## Category 2 -- Schema-driven form generation

**Read this skeptically, as instructed.** Every candidate here is built around JSON Schema (or Zod/SimpleSchema) semantics. ### The direct answer: build it

Given every text-anchoring library anchors to *rendered prose*, none has a native concept of "this comment points at JSON Pointer `/records/42/status`," and the one mechanism that actually matches this problem shape (structured position + explicit staleness flag) is not a library at all -- the honest recommendation is: **build a lightweight custom anchor primitive, and borrow the two most credible behavioral references found (Hypothesis's "orphan" concept, GitHub's "outdated" concept) rather than adopt any researched library as a dependency.**

Concretely, the primitive this research points toward: store per comment `{recordId or documentId, field/path address, a snapshot or hash of the value at comment time}`. On render, resolve the path -- a missing path is "orphaned" (record/field deleted or moved), a resolved path whose value no longer matches the snapshot is "stale" (data changed since the comment). That is Hypothesis's orphan model and GitHub's outdated model, reimplemented against a JSON/YAML tree instead of DOM text, at an estimated cost of a few hundred lines rather than a dependency plus an integration-fighting exercise (Hypothesis specifically is a heavy sidebar app, not an embeddable primitive -- a poor match for "not overly opinionated" even where it's the most mature prior art).

**Touch is a first-class design constraint here, not an afterthought**, since hover cannot exist on touch and the whole feature is anchored interaction:
- Use a persistent, always-visible marker/badge (comment count) next to any record or field with a thread -- inherently tap/click-agnostic, and the same physical affordance GitHub Mobile, Retool, and Airtable actually use.
- Tap/click opens the thread directly; an optional hover *preview* on desktop is a progressive enhancement layered on top, never the only path.
- Thread display: side panel or popover on desktop; a full-width bottom sheet on narrow viewports, not a hover-anchored popover.
- Composing: tapping the badge should immediately expose a text input -- no secondary "hover to reveal a small + icon" step.
- No library researched demonstrates a touch-adapted version of this UX for free -- even GitHub, the best-resourced example found, shipped mobile commenting as a separate, later feature rather than getting it automatically from the desktop implementation.

## Leading option vs. the deliberately-more-boring alternative

**Leading option** -- most consistent with "not overly opinionated," most schema-driven-DSL-friendly, and the one that best respects the finding that the hard parts (variants, extensible, typed ref, annotation) are custom regardless of library:

- **TanStack Table** for the row/list view -- headless, MIT, framework-agnostic core, and the only grid researched with a real architectural story for genuinely different desktop-vs-mobile renderings (a table and a card stack from one column/row model) rather than a single layout fought into responsiveness.
- **CodeMirror 6 + `@codemirror/lang-yaml`** for the raw-YAML fallback *and* as the decoration substrate if any inline-in-source comment anchoring is wanted -- its `Decoration`/`RangeSet`/gutter API is genuinely the cleanest of anything researched in any category, verified live, unopinionated, MIT.
- **`yaml` (eemeli/yaml)** for parsing, specifically because it is the only parser confirmed to carry per-node source ranges and comment preservation, which the anchoring feature needs regardless of which rendering libraries are chosen.
- **Hand-built** structured-record rendering, variant switching, inheritance/override visual state, typed-ref pickers, and the comment-anchor primitive itself -- because no adoptable library in categories 2, 3, or 5 covers these, and the schema already declares everything a renderer needs to generate them (see below).

**Boring alternative** -- a fully-baked, batteries-included grid instead of a headless one, for a team that would rather configure a widget than build rendering from scratch:

- **Tabulator** in place of TanStack Table -- MIT, no build step, moderate weight, ships a genuinely built-in non-scroll mobile fallback (`responsiveLayout: "collapse"`) that also functions as a detail-drilldown mechanism, and typed dropdown editors out of the box for enum/ref fields. Trades TanStack's "build exactly the UX you want" flexibility for "install and go," at the cost of owning more of the DOM/CSS than a headless library would concede.
- Everything else (raw YAML fallback, parser, and all hand-built pieces) stays the same -- this substitution is scoped to the table layer only, since that's the one category with a real, low-risk, boring, well-verified alternative.

DataTables deserves a name-check as the single most battle-tested library in the entire survey (oldest, most active release cadence, free child-rows + Responsive extension solving drilldown and mobile with one mechanism) -- but its hard jQuery dependency is a real architectural cost for a modern non-jQuery stack, which is why it's a runner-up rather than the boring pick.

## What can be done with no library at all

The schema-driven angle genuinely makes some of this research redundant, and that is worth stating plainly rather than talking around it:

- **A `view` document's `fields:` list already IS a column/field configuration.** Grid libraries and form generators exist substantially to give you a place to declare column order, labels, and formatting -- the dialect already provides that place (`view/1`, `form: table|card|summary`, `fields:` in render order, per-entry `label`/`format`/`link`/`group`/`when`). A plain loop over `view.fields` rendering `<td>`/`<dt>`/`<dd>` elements replaces most of what a grid or form library's configuration layer exists to save.
- **`enum`/`ref` fields already declare their own legal set** (`values:`, `values_from:`, or a `ref: to:` resolution) -- deriving a `<select>` from that is a direct, trivial mapping. No form-generator's UI-schema layer is needed to get "dropdown for an enum," which is exactly the feature every schema-driven form library treats as a headline capability.
- **`variants:` already names the discriminator and the exact fields each value adds** (`on:`, `when:`) -- a conditional render switch keyed on that field is a direct read of the schema, not a mapping through a library's `oneOf`-to-widget translation layer. This is arguably *simpler* to hand-write against the dialect directly than to transpile into JSON Schema `oneOf` and then have a library re-derive a switcher UI from it -- which is exactly what Category 2's skepticism predicted going in.
- **100-500 rows does not need a virtualized, performance-engineered grid.** Every performance-oriented feature researched (Glide Data Grid's canvas rendering, AG Grid's row virtualization) is solving a problem this project doesn't have at this row count. A naive JS array sort/filter and full re-render is entirely tractable here.

Where a library still earns its keep despite the schema being self-describing:
- **Accessible, well-tested table interaction chrome** -- keyboard navigation, ARIA roles, resizable/reorderable columns. This is real, nontrivial, previously-solved UX and accessibility work; reinventing it is a bad trade even though the *configuration* layer is redundant.
- **The mobile responsive-collapse mechanism** (Tabulator's `responsiveLayout: collapse`, DataTables' Responsive extension) -- nontrivial CSS/JS engineering worth not reinventing, and the one place a library's built-in mobile answer is demonstrably better than what a from-scratch team would likely ship first.
- **The code-editor decoration/anchoring substrate** (CodeMirror 6) -- position tracking across arbitrary text edits is genuinely hard, low-level work, not something the schema helps with at all, and not worth reinventing.

So the honest shape of the recommendation is: adopt little, and adopt narrowly -- a table-interaction-chrome library (if any), a mobile-collapse mechanism, and CodeMirror for the raw-text/anchoring substrate -- and hand-write the schema-driven rendering, variant switching, and comment-anchor logic directly against the dialect, because the dialect already did most of the "configuration" work a general-purpose library exists to save.

## Where the biggest risk of picking wrong is

**Adopting a heavy, opinionated library for the easy 80% of the problem while the hard 20% still has to be hand-built regardless of what's adopted.** Nothing researched -- not the grids, not the form generators, not the tree editors -- natively models `variants:`, `extensible:`'s inherited-vs-overridden visual state, or typed `ref:` pickers against a legal set drawn from elsewhere in the document graph. That work is custom no matter which library is chosen. If the library picked for the "easy" rendering is heavy or opinionated (AG Grid's paywalled drilldown/annotation, Handsontable's now-restrictive license, Formily's app-owning reactive-state engine, SurveyJS's proprietary survey format), the team pays its integration and mobile-fighting cost *in addition to* still hand-building every hard part -- worse than building from scratch, not better.

**The sharper, category-5-specific version of this risk**: treating "find a comment-anchoring library" as a solvable shopping problem is itself likely the wrong turn. Every library researched anchors to prose text or a whole rendered page; none anchors to a structured data field. A team that spends real time evaluating Hypothesis, Recogito, or a ProseMirror-comment fork as adoptable dependencies for *this* feature is at risk of losing the search itself -- the evidence points at building the anchor primitive on day one and treating the libraries in that category as UX references, not dependencies.

A secondary, easy-to-miss risk: **license drift on candidates that still read as "open source" in older material.** Handsontable specifically has moved to a non-commercial-only free tier since much of what's written about it online was published -- a team that picks it based on older comparisons or blog posts would discover the license problem late.
