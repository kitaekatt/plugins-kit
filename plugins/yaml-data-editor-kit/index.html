The plugin-level documentation and packaging for the YAML data editor kit, covering the dialect spec, architecture notes, dispatch binding, and editor research.

This directory holds the documentation and packaging around the yaml-data-editor-kit library: the dialect specification, the architecture notes, the binding note for the dispatch side, and the editor research. The implementation code sits one level down and carries its own page, so there is no source here to read; this is the design record around it. The documents divide by job: the specification of the dialect, the story of why the kit exists and what shape it has, the seams to other systems, and the manifests that ship it. Each also states what kind of text it is: the spec is normative, the motivation is background, the binding note is a boundary, and the editor research is still undecided.

Where to start

Open the dialect spec, docs/dialect.md, if your task is authoring or reviewing a profile declaration; it is the normative text the other documents cite. If you need to know what this plugin is and what it refuses to be, start with the charter, CLAUDE.md.

Routes

  • Why the kit exists, then its current shape: docs/motivation.md -> docs/architecture.html. The motivation note ends by pointing to the architecture page for the current package boundaries.
  • The spec, then the record of how it changed: docs/dialect.md -> docs/dialect-gaps.md. The gap record cites the spec verbatim, row by row, so a citation there is a check, not a pointer.
  • The editor decision menu, read against the dialect it grounds itself in: docs/dialect.md -> docs/editor-library-research.md.

The dialect and its history

docs/dialect.md
The specification of the dialect itself: the three document kinds, field types, and field annotations. It is the normative text; open it when authoring or reviewing a profile declaration.
docs/dialect-gaps.md
The findings from writing the first profile and implementing the loader, each row marked applied or unapplied with a verbatim citation into the spec. Open it when a construct looks missing or a spec question is unsettled.

The kit's shape and story

docs/motivation.md
The neutral restatement of the originating specification: the problem, the core idea, and what the kit is and is not. Background, not a contract; the spec and the code win over it.
docs/architecture.html
The package shape and implementation status, with the four-package diagram and the declared file seam. A snapshot at version 0.15.9 while the manifests say 0.17.0, so read it as the shape's history, not current behavior.

The seams to other systems

docs/content-pipeline-binding.md
What the dispatch side binds to content-pipeline-kit and what it deliberately does not, including the two extension points that define the dispatch seam. Open it before touching dispatch behavior or re-litigating a binding choice.
docs/editor-library-research.md
The decision menu of browser libraries for the editor surface that Databench owns, with per-candidate license, maintenance, and demo-verification status. Research only: no decision has been made and no code was written.

Charter and packaging

CLAUDE.md
The plugin's charter: what the plugin is (a library, not a tool), the profile boundary, the file seam, and the four packages. Agent-facing guidance, but the clearest statement of what this plugin refuses to do; open it before changing plugin scope.
.claude-plugin/plugin.json
The plugin manifest: name, version, the bootstrap dependency, and keywords. Check it when the version moves or the plugin fails to load.
pyproject.toml
The Python packaging: project metadata, dependencies, and the discovery of the package under the lib directory. Open it when adding or moving a dependency.
bootstrap.json
The shared-library declaration that exposes the package to the plugin, the content-pipeline-kit dependency, and the venv import check. Open it when the plugin's external imports change.
