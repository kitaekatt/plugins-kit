Multi-agent code review for local git changes: partitions a diff into chunks, fans out parallel reviewer and validator subagents, and renders confirmed findings as markdown.

This page covers the git-code-review skill for local git changes. It turns a diff range into a partitioned bundle, sends parallel reviewers and validators over the chunks, and renders confirmed findings as markdown. The skill also resolves review profiles from layered configuration, collapses previously declined findings on re-runs, and surfaces path-scoped submit gates from guidance files. The organizing idea is separation of mechanical preparation from model-driven judgment: the bundle is built once, reviewers run per lane and chunk, validators re-check claims, and markdown rendering happens only after confirmation.

Where to start

Open plugins/git-kit/skills/git-code-review/SKILL.md for the review step order, fan-out rule, and failure behavior. All documents here are generated, so change the generator rather than the file.

Routes

  • Run a review
    1. Resolve the review-profile table and stop if any layer reports a finding.
    2. Prepare the diff bundle once, with the inferred or explicit range.
    3. Fold in user-selected untracked or unstaged files, then re-prepare only when needed.
    4. Dispatch reviewer lanes per reviewer and chunk, then validate flagged issues.
    5. Render confirmed findings as markdown and record declined findings.
  • Audit changed Markdown
    1. Check whether the subject-lens Markdown skill is available.
    2. Claim changed Markdown files when it is, and degrade to generic review when it is not.
    3. Route claimed files to the matching detect lane by file shape.
    4. Skip trivially small changes and report them as mechanically checked.
    5. Render subject-lens findings as a separate labeled section.
  • Configure lanes
    1. Edit the shipped, user, or project profile layer.
    2. State a complete model list with an effort for every entry.
    3. Run the profile renderer in check mode before starting a review.
    4. Fix every reported finding before the review can start.
  • Author submit gates
    1. Add a submit-gate block to a guidance file.
    2. List path prefixes or globs under the Applies to line.
    3. Let the review surface the gate when a changed file matches its scope.
    4. Discharge the gate from evidence in the change, not from memory.
