Bootstrap skill reference for engine behavior, manifest configuration, CLI commands, and remediation

This directory is the bootstrap plugin's reference skill: what the engine does on session start, how manifests configure it, which terminal commands drive a pass, and how remediation is decided. The skill file holds the fact set an agent answers from directly, and a companion set of long-form documents holds the mechanics, one document per subject, cross-referenced by name. Healthy bootstrap is silent, so most questions here start from a log line, a fix-all message, or a state file rather than from output. Pick the document that matches what you are debugging and follow its cross-references instead of browsing.

Where to start

Open SKILL.md first: its facts are what the agent loads on demand, and each one names the long-form document that carries the mechanics. If the subject is already clear, go straight to the matching group below.

Routes

  • Converge an update by hand: which layer a change goes live in, per the measured tables in references/plugin-reload-lifecycle.md; then whether the engine version has caught up, per the update-lifecycle fact in SKILL.md; then the force-pass and reset commands, bootstrap run and bootstrap reset, in references/bootstrap-cli.md.
  • Decide escalate versus defer: the rule and the API in references/deferred-requirements.md; when the missing precondition is a plugin, the install mechanics continue in references/action-triggered-install.md.
  • Author a plugin's manifest: the config section for user settings in references/plugin-setup-pattern.md; the field forms in references/manifest-reference.md; then the download-versus-system rubric in references/dependency-philosophy.md for every tool entry.

The skill's fact set

  • SKILL.md: the load-bearing fact set: session-start outcomes, single-session update convergence, the force-pass lever, the cooldown-reset protocol, and the two remediation phases. Open it first for any bootstrap question; every fact names the document that holds its mechanics.

Engine behavior and lifecycle

  • references/engine-internals.md: how a pass runs: the detached hook, the engine phases in order, the pending-file display relay with its age stamp, registry self-repair, and the single-instance lock. Open it when the question is what the engine did.
  • references/plugin-reload-lifecycle.md: which change went live after an edit or an update: code content, registration, and re-firing each go live differently, with the measured tables that settle the folklore. Open it before advising a restart or a plugin reload.

Manifest and configuration

  • references/manifest-reference.md: the manifest schema and per-field reference: every phase key, merge and layering rules, environment exports, and the config section. Open it when writing or debugging a manifest entry.
  • references/dependency-philosophy.md: why the engine downloads some tools and defers to system installs for others, with the rubric applied to the common tools. Open it before choosing a download block over an install command.
  • references/plugin-setup-pattern.md: how a plugin declares user-specific settings through the manifest config section, plus the legacy setup CLI it replaces. Open it when a plugin needs API keys, preferences, or paths.

Terminal commands and interpreters

  • references/bootstrap-cli.md: every verb of the terminal command: status and follow, forced run, reset, profile selection and state, and the interpreter resolvers, with exit codes. Open it for anything run from a terminal.
  • references/python-interpreter.md: the interpreter contract: which surfaces get BOOTSTRAP_PYTHON versus BOOTSTRAP_PROJECT_PYTHON, the copy-ready call-site expressions, and the opt-outs. Open it when a script or terminal cannot find the right interpreter.

Remediation

  • references/remediation-reference.md: check method and remediation for every condition category, the UX ladder that ranks every surfacing, and the AUTO versus ASK decision with its structural exceptions. Open it when a fix-all message needs explaining.

Patterns for plugin authors

  • references/deferred-requirements.md: the escalate-versus-defer rule for preconditions only some capability needs: the API, the handoff file the point of need reads, and the consumption protocol. Open it when writing a custom check.
  • references/action-triggered-install.md: the plugin-install instance of deferral: declare the plugin manual, preflight at the moment of need, install on consent, and retry without a restart. Open it when wiring an optional plugin dependency.
  • references/library-consumption.md: every way a Python process reaches a shared library, which modes are supported, and why the pip route is not. Open it when a consumer outside the plugin world needs one.
  • references/durable-project-data.md: where a plugin writes its own data: the durable and ephemeral project locations, user-scoped data, and the rule that keeps writes out of source checkouts. Open it when choosing a path for generated artifacts.
  • references/fleet-management.md: how an administrator lands bootstrap on every machine through the ensure-bootstrap hook, with the opt-out and the re-run contract. Open it when a fresh clone lacks bootstrap.
