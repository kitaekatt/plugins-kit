Bootstrap plugin that prepares user machines for marketplace plugins by installing tools, Python environments, and configuration, and exposes its command, hooks, shell resolvers, maintenance scripts, and plugin-development skill.

Every plugin in this marketplace can ship scripts, but the machines they land on have no guarantee of the tools, the Python, or the configuration those scripts need; this plugin is the layer that closes the gap. At session start it reads each installed plugin's manifest and brings the machine into the state the plugin declared: tools installed, a virtual environment built, shared libraries linked, configuration seeded. The engine, the SessionStart launcher, and the skill reference sit behind pages of their own; everything here is the face around that work. A healthy machine is silent: no output at session start means every check passed, and what genuinely needs the user is held in one fix-all message.

Where to start

Open README.md first: it is the account of what a pass does, the bootstrap command, and where the plugin writes outside its own directory. For behavior rather than story, scripts/bootstrap_cli.py is where every terminal verb resolves to.

Routes

  • Terminal pass: scripts/bootstrap.sh -> scripts/bootstrap_cli.py. The shim locates the plugin tree and an interpreter, then hands the arguments to the CLI, which runs the same engine pass as the session hook.
  • Reset a stuck project: scripts/bootstrap.sh (reset) -> scripts/bootstrap-reset-cooldown.sh. The shim delegates reset to the bash lever, which clears the cooldown stamp so the next session start is a real pass.
  • Force the environment phase: scripts/env-reset-cooldown.sh -> scripts/bootstrap-reset-cooldown.sh. It deletes the phase stamp, then calls the sibling lever so the cooldown does not gate the next pass.
  • Put a project fleet on a version floor: scripts/install_bootstrap_hook.py -> templates/ensure-bootstrap.sh. The lever renders the template with the current version into the project's hook settings; the written hook installs or updates the plugin via the claude CLI.

What the plugin declares about itself

  • bootstrap.json - its own manifest: a checksummed jq download, the hard dependency on the claude CLI, and the marketplace the pass keeps refreshed.
  • pyproject.toml - the Python project: version, three dependencies, and the entry point that points into the shared library.
  • .claude-plugin/plugin.json - the name, version, and description Claude Code shows for the plugin.
  • defaults/config.json - the default configuration: self-setup tools, PATH entries, and the Windows stub-Python check.

Session hooks

  • hooks/hooks.json - declares both hooks: the SessionStart launcher, which has its own page, and the UserPromptSubmit relay below.
  • hooks/userpromptsubmit/bootstrap-display.sh - the UserPromptSubmit hook: surfaces the pass's one-time verdict on the first prompt, rescues a session whose SessionStart never fired, and picks up mid-session updates.

The terminal levers

  • scripts/bootstrap.sh - the thin shim for the bootstrap command: locates the installed plugin tree and an interpreter, then execs the CLI.
  • scripts/bootstrap_cli.py - the CLI face: status, run, codex-hook, reset, python, install-hook; holds the single-instance discipline and the tail loop.
  • scripts/bootstrap-reset-cooldown.sh - clears the per-project cooldown stamp and session guard so the next session start is a real pass; the target of the reset verb.
  • scripts/env-reset-cooldown.sh - deletes the environment phase stamp to force that phase next session, then invokes the sibling lever to clear the cooldown.
  • scripts/diagnose-python-venv.sh - read-only diagnostics for uv, the Windows junction problem, and the bootstrap and unreal-kit venvs; the first stop when a venv looks wrong.
  • scripts/install_bootstrap_hook.py - writes the fleet hook into a project: renders the template, adds the hook entry, refuses a read-only target before writing.
  • templates/ensure-bootstrap.sh - the hook the lever renders into a project: installs or updates the plugin when missing or below the version floor, and never blocks a session.

Shell interpreter resolution

  • shell/project-python.sh - the bash and zsh resolver that keeps BOOTSTRAP_PROJECT_PYTHON in step with the current directory; sourced by the hook preamble and interactive terminals.
  • shell/project-python.ps1 - the PowerShell twin, dot-sourced from the profile line the engine appends.

Back-compat engine wrappers

  • engine/bootstrap_engine.py - a backward-compat wrapper: forwards direct callers to the engine in the shared library; on import failure it records a display message so the error still reaches the user.
  • engine/config.py - a thin re-export for callers that import the config module by its old path.

Plugin-authoring guidance

  • skills/plugin-dev/SKILL.md - the entry point: when to choose REQUIRED, REFUSE, or DEGRADE for a cross-plugin edge, and where the model-declaration format lives.
  • skills/plugin-dev/references/optional-plugin-dependencies.md - the full contract: the two questions, the three runtime states, each branch's mechanics, and the reviewer checklist.
  • skills/plugin-dev/references/enabling.md - the enabling contract: a consented probe that discloses a live capability in at most three lines, silent when it is absent or too old.
  • skills/plugin-dev/references/model-declaration.md - the one format every plugin uses to declare which models may do a unit of work, and the shape-only validator it specifies.
  • AGENTS.md - agent-facing standing rules: the harness-neutral core, harness layers that may adapt but never fork it, and thin project-level bootstrap files.
