The p4-kit scripts that prepare Perforce changelists for code review, dispatch and parse review lanes, render review profiles, and guard the plugin's bootstrap venv.

Six entry points for the p4-kit Perforce review plugin, and nothing else. Each one first re-execs the process under the plugin's bootstrap-provisioned venv, then hands the real work to a shared library: diff chunking, the review pipeline, lane dispatch and profile resolution all live in bootstrap_lib and llm_kit, linked onto this venv by the bootstrap plugin. The scripts here are the stable seams the p4-code-review skill invokes, plus one vendored runtime guard and one legacy-cleanup sweep. That split decides where a problem lives: a review that misreads the diff is in the shared libraries, while a review that cannot start at all -- wrong interpreter, missing venv, too-old dependency -- is in this directory.

Where to start

Start with plugins/p4-kit/scripts/prepare_review.py: it is the only script here that does real work, and the bundle it writes is the input the lane dispatch and parsing consume. For how any of the scripts survives a missing or stale bootstrap, read plugins/p4-kit/scripts/bootstrap_guard.py instead; its docstring is the design note.

Routes

  • Review a Perforce changelist
    1. plugins/p4-kit/scripts/prepare_review.py <CL> -- gathers the diff into chunks, the changed files with their ancestor review rules, and the p4 hygiene scans; the bundle goes to stdout and the diff chunks to disk.
    2. plugins/p4-kit/scripts/run_review_lane.py -- one endpoint lane runs per diff chunk, pointed at the bundle by path and chunk index. Before dispatch the wrapper probes the installed llm-kit and refuses a too-old one with the missing flag named.
    3. plugins/p4-kit/scripts/parse_review_lane.py -- parses one native lane's JSON output back into the pipeline.
  • Trace a script's cold start
    1. plugins/p4-kit/scripts/bootstrap_guard.py -- every entry script imports this vendored guard at the top and calls its re-exec, so the process runs under the plugin venv before any shared-library import.
    2. The shared-library import then either succeeds, or the guard exits with code 3 and the install-the-bootstrap message instead of a traceback.

Preparing the review

  • plugins/p4-kit/scripts/prepare_review.py -- gathers a changelist's full review context: diff chunks, changed files with their ancestor review rules and submit gates, reconcile and resolve scans, shelving and shelf-drift checks, and optional claimed files with their pre-images. The only heavyweight script here; open it for p4 behavior questions such as UTF-16 adds, stale opens, and foreign-client changelists.

Review lanes

  • plugins/p4-kit/scripts/run_review_lane.py -- dispatches one configured endpoint lane. A thin wrapper that owns bootstrap setup and the capability probes; the seam call itself goes to llm_kit, and a too-old owner is refused with the missing flag named rather than a generic error.
  • plugins/p4-kit/scripts/parse_review_lane.py -- parses one native lane's JSON output. Same guard-and-delegate shape, with the parsing itself in bootstrap_lib.

Review profiles

  • plugins/p4-kit/scripts/render_review_profiles.py -- renders the resolved code-review profile table for a project root. It exists so the skill has a stable per-plugin path; resolution, merging and rendering live in the shared resolver.

Runtime guard and cleanup

  • plugins/p4-kit/scripts/bootstrap_guard.py -- the canonical vendored guard, stdlib-only on purpose so it can run when bootstrap is absent. It detects provisioning, re-execs the process under the plugin venv, and turns a missing shared library into an actionable message. A drift test fails if a vendored copy differs from this one.
  • plugins/p4-kit/scripts/cleanup_legacy_config.py -- removes legacy per-project p4-kit config files. A no-op sweep registered in the plugin manifest, safe to leave in place until the field is clean.
