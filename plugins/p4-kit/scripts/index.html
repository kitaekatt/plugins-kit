The p4-kit scripts that prepare Perforce changelists for code review, dispatch and parse review lanes, render review profiles, and guard the plugin's bootstrap venv.

Six scripts in plugins/p4-kit/scripts back the p4-kit code-review skill. Three are thin launchers that fix up the Python environment and hand off to a shared library; one, plugins/p4-kit/scripts/prepare_review.py (about a hundred kilobytes), does the real Perforce work; one guards the plugin's bootstrap venv; and one sweeps out a dead config file. Open plugins/p4-kit/scripts/prepare_review.py first: it is the script you run on a changelist, and reading its docstring puts you in the review flow. The shared logic the thin launchers delegate to lives outside this directory, so most of what you need to change lives one level down in the plugin's lib or in a sibling plugin.

Where to start

Open plugins/p4-kit/scripts/prepare_review.py and read its docstring: it covers every p4 call the script makes, the full bundle JSON schema, the claim and ledger modes, and all three CLI shapes. If a script exits with a bootstrap error or picks the wrong interpreter, open plugins/p4-kit/scripts/bootstrap_guard.py second; the re-exec and venv logic is documented in its comments.

Prepare a changelist

  • plugins/p4-kit/scripts/prepare_review.py Describe the changelist (shelved or submitted), resolve depot files to local paths, walk each file's ancestors for review rules, run the workspace hygiene scans, split the diff into chunk files, and print the bundle JSON on stdout. --claim holds selected files out of the generic fan-out, --ledger-record files declined findings, and --cleanup undoes a shelf this run created. Open it to change what a review sees or how the bundle is shaped.
  • plugins/p4-kit/scripts/bootstrap_guard.py Canonical copy of the bootstrap-presence guard, vendored byte-for-byte into each plugin that needs it; a drift test asserts the copies stay in sync. Stdlib only, so it can run when bootstrap is exactly what is missing. It checks for the per-plugin bootstrap.log marker, exits 3 with an install-bootstrap message when it is absent, locates the venv interpreter, and re-execs the process under it (spawn and wait on Windows). Open it to change the failure message, the venv detection, or the re-exec behavior.
  • plugins/p4-kit/scripts/cleanup_legacy_config.py Session bootstrap step that deletes the legacy per-project config files earlier releases wrote. A no-op when nothing is present, so it stays wired in for several releases and is then deleted along with its bootstrap hook entry. Open it when you retire those last files.

Thin entry points

  • plugins/p4-kit/scripts/parse_review_lane.py P4's side of lane parsing: re-exec under the plugin venv, then run the shared lane-output parser and exit with its code. Open it when a lane's JSON output changes shape.
  • plugins/p4-kit/scripts/run_review_lane.py Dispatches one configured endpoint review lane. The wrapper owns the bootstrap setup and the capability probes; the seam-calling implementation lives in a sibling plugin's shared library. The probes parse throwaway argv to detect a too-old owner and exit 2 with an update instruction instead of dispatching into an incompatible one. Open it to add a probe for a new shared-library flag.
  • plugins/p4-kit/scripts/render_review_profiles.py Prints the resolved review-profile configuration plus provenance. A stable per-plugin path so the skill never reaches into another plugin's tree; the resolver itself is shared. Open it when the profile table looks wrong.

Review mechanics worth knowing

  • Every entry point re-execs under the plugin venv before it imports shared libraries, and re-exec is a no-op when the process is already inside the venv. plugins/p4-kit/scripts/bootstrap_guard.py and plugins/p4-kit/scripts/prepare_review.py say why: a plain python or uv run lands in an environment that lacks the shared-library link, and the venv check compares sys.prefix rather than interpreter paths.
  • Hygiene failures and clean results are never folded into one list: a scan that could not run is recorded under the bundle's hygiene_incomplete key with the reason, while an empty unreconciled list means the scan ran and found nothing. A stale_open entry means the changelist will fail p4 submit as it stands.
  • Diff text is never inlined: it is partitioned into chunk files beside the review bundle and indexed by diff_chunks so one large changelist fans out across parallel reviewers. Ledger keys let previously declined findings render collapsed instead of being re-litigated on the next review of the same changelist.
  • Claimed files are carved out of the generic fan-out and materialized with their #have pre-image under the bundle's pre-images directory; an exclusion glob prefixed with ! beats every positive claim pattern. --claim is refused for submitted changelists, because post-change pre-images would misrepresent the change.
