The library for LLM-in-the-loop batch content pipelines, providing an attributed store, freshness engine, durable execution plane with run tracking and worker protocol, delivery modes, VCS seam, and audit.

This is the content_pipeline package: the generic machinery the content-pipeline-kit plugin ships for LLM-in-the-loop batch content work, with no project-specific knowledge baked in. Every capability is its own subpackage, and the root re-exports nothing but the version, so importing one piece never pulls in the others and the import graph stays a strict DAG. It reads as a stack: a data substrate that tracks what still needs generating, plus a validator contract at the bottom; an LLM binding and pass orchestration in the middle; durable run tracking, delivery modes, and auditing on top. Because it is project-free, a consumer wires its own row shapes, policy, and storage behind injected callables rather than the library reaching into its code.

Where to start

Open plugins/content-pipeline-kit/lib/content_pipeline/__init__.py first: its docstring states the full scope and the strict-DAG import rule, so it is the fastest way to see which subpackage answers your question. If you are wiring the package into a project rather than reading it, plugins/content-pipeline-kit/lib/content_pipeline/default_config.yaml is the only file here that is not a code module.

Routes

  • Run a tracked batch
    1. prepare_run -- gate sequence plus freshness check; returns the claimable wave
    2. run_wave (inline driver) -- executes the wave through the store, one unit at a time
    3. finalize_run -- re-parses and applies every accepted unit, serially in ordinal order
    4. unfinished_units -- recovers the not-yet-terminal set after a halt so a resume knows what is left
  • One worker through the protocol
    1. claim -- take a unit with its fencing token and lease
    2. read -- fetch the prepared request (system and user text)
    3. submit -- deliver the answer text; it is parsed, validated, then accepted or rejected
    4. finalize -- the orchestrator applies the accepted payload
  • Freshness scopes the work
    1. needs_generation (freshness classifier) -- which units are stale or missing
    2. prepare_run -- records a terminal skip for every up-to-date unit
    3. generate only the remaining wave, so a fresh unit is never re-paid
  • Deliver the output
    1. apply_inplace -- rebuild machine-owned rows purely from the store, leaving human rows untouched
    2. deliver_changeset -- drive the injected VCS seam around the write (placeholder changeset, moves, description)

The package and its import rules

  • plugins/content-pipeline-kit/lib/content_pipeline/__init__.py -- the full scope plus the strict-DAG rule in one docstring; it re-exports nothing but the version.
  • plugins/content-pipeline-kit/lib/content_pipeline/default_config.yaml -- machine-global defaults (cache directory, model overrides); per-project values live in project config.

Data, freshness, and validation

  • plugins/content-pipeline-kit/lib/content_pipeline/store/__init__.py -- the attributed canonical store and its projection; the source of truth delivery rebuilds from.
  • plugins/content-pipeline-kit/lib/content_pipeline/freshness/__init__.py -- the two-tier content-hash engine that decides what still needs generating.
  • plugins/content-pipeline-kit/lib/content_pipeline/providers/__init__.py -- the tiered context-provider registry: the layered context a generation call is built from.
  • plugins/content-pipeline-kit/lib/content_pipeline/validate/__init__.py -- the one-rule-many-call-sites validator contract, with the floor guard and riders.

The LLM binding

  • plugins/content-pipeline-kit/lib/content_pipeline/llm/__init__.py -- transport, cache, cost, and budget over an OpenAI-compatible endpoint; reuses llm-scripting-kit for key and client.

Pass orchestration

  • plugins/content-pipeline-kit/lib/content_pipeline/pipeline/__init__.py -- the single-pass and convergence-loop shapes, plus gates and the work-unit strategies a run walks.

The durable run plane

  • plugins/content-pipeline-kit/lib/content_pipeline/execution/__init__.py -- the SQLite run store, atomic claims with fencing tokens, and the bounded status digest; the largest subpackage.
  • plugins/content-pipeline-kit/lib/content_pipeline/execution/protocol.py -- the versioned JSON worker protocol (claim, read, submit, fail, renew, status, pause, resume, finalize) as mountable handlers; no console script.
  • plugins/content-pipeline-kit/lib/content_pipeline/execution/controller.py -- prepare_run and finalize_run bracket a run; also the shared halt response and terminal-skip bookkeeping.

Delivery and the VCS seam

  • plugins/content-pipeline-kit/lib/content_pipeline/deliver/__init__.py -- the two modes: in-place mutation with a do-no-harm marker and revert, and append-only projection with a .bak rollback.
  • plugins/content-pipeline-kit/lib/content_pipeline/vcs/__init__.py -- the backend-agnostic changeset seam: a git default and a null backend; Perforce ships in p4-kit, not here.

Audit, provenance, and human-in-the-loop

  • plugins/content-pipeline-kit/lib/content_pipeline/audit/__init__.py -- the audit framework that reuses the runtime's own classifiers, so a finding is the runtime's verdict, not a second rule set.
  • plugins/content-pipeline-kit/lib/content_pipeline/audit/auditor.py -- the six finding kinds and the injected AuditSpec that carries the runtime callables.
  • plugins/content-pipeline-kit/lib/content_pipeline/provenance/__init__.py -- the provenance surface: call audit, records, replay, and snapshots.
  • plugins/content-pipeline-kit/lib/content_pipeline/roundtrip/__init__.py -- the human-in-the-loop abstraction: typed questions to a person and their returns, mid-run.

The CLI scaffold

  • plugins/content-pipeline-kit/lib/content_pipeline/cli/__init__.py -- the reusable scaffold: arg dispatch, scope filtering, did-you-mean, uniform YAML output, and stable exit codes.
  • plugins/content-pipeline-kit/lib/content_pipeline/cli/run.py -- command adapters over execution (argv only, no logic); the protocol command reads a JSON envelope, preferably on stdin.
  • content-pipeline-kit Content-pipeline-kit plugin packaging: bootstrap configuration, public API surface contract, one-unit worker agent, consumer contract checker, and parallel wave workflow.
