Execution drivers that claim units from a prepared wave and record their outcomes through the durable run store; how each unit's text is produced varies by driver.

This package is the place where prepared work gets executed. A driver claims units from a wave and moves each one from PENDING through the durable run store to a terminal or halted state; the store-side claim-and-record contract is the only thing a driver must satisfy, and it is what both shipped drivers share. The two diverge on how a unit's text gets produced: one runs a unit synchronously in the calling process, the other launches background Claude sessions that submit their work back through the protocol. The contract and the graph-looping trap are written in the package docstring, and both drivers repeat the trap in their own module docs. The surrounding execution package defines the unit states and the store a driver drives, and the session-recipients plan sequenced these drivers.

Where to start

plugins/content-pipeline-kit/lib/content_pipeline/execution/drivers/__init__.py first, because its docstring states what a driver must satisfy, flags the graph-looping trap before either driver repeats it, and sketches the shape of the drivers that follow. Then the two drivers by size: plugins/content-pipeline-kit/lib/content_pipeline/execution/drivers/inline.py for the in-process path, plugins/content-pipeline-kit/lib/content_pipeline/execution/drivers/claude_bg.py for the background-session one.

Hazard before you loop

  • On a graph strategy an empty wave is not proof the run is complete. It also means the successor is blocked on a predecessor that is ACCEPTED but not yet applied, so a caller that loops ready_wave and the driver without interleaving finalize_run sees the wave stay permanently empty after the first accept. Use unfinished_units to tell complete from blocked. Both plugins/content-pipeline-kit/lib/content_pipeline/execution/drivers/inline.py and plugins/content-pipeline-kit/lib/content_pipeline/execution/drivers/claude_bg.py carry this caveat; the required loop shape is in the module docstring of the wave module.
