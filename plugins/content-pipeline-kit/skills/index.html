The content-pipeline skills for the pipeline domain, background-session orchestration, workflow-lane orchestration, and one-unit worker execution.

These four skills are the prose layer of the content-pipeline-kit plugin: each is a procedure for Claude rather than code, and each covers one role in an LLM-in-the-loop batch content pipeline. The domain skill carries the architecture vocabulary and the abstraction map, plus step-by-step references for building a new pipeline, porting an existing one, and choosing which opt-in guardrails to adopt. The other three split the run machinery by who is acting: one drives a whole run through a background-session dispatcher, one drives it through the native Workflow tool, and one is the procedure a single worker session follows to complete exactly one work unit. The split is deliberate -- orchestrator and worker are separate sessions with different context and different failure modes, so every one of them keeps unit content out of the supervising context.

Where to start

Start with content-pipeline-domain/SKILL.md if you are designing, building, or porting a pipeline: it carries the vocabulary the other three skills assume and indexes the references below. If you are driving a run right now, go straight to the orchestration skill for your lane -- background-pipeline/SKILL.md for a background-session dispatcher, workflow-pipeline/SKILL.md for the Workflow tool.

Routes

  • Drive a run through background sessions: background-pipeline/SKILL.md -- prepare the wave, run dispatch_wave, read the batch-boundary status digest, then finalize_run.
  • Run a wave through the Workflow tool: workflow-pipeline/SKILL.md -- verify the four preconditions, build the wave with build_wave_args, invoke the Workflow tool, reconcile against the store, then finalize.
  • Complete one unit as a worker: execute-work-unit/SKILL.md -- read, write the fenced answer, author the submit envelope, submit, and report failure on exhaustion.
  • Wire a consumer onto worker sessions: content-pipeline-domain/references/session-recipients.md for the protocol mount and the allowlist, then content-pipeline-domain/references/workflow-lane.md for how the workflow lane differs.
  • Stand up a new pipeline: content-pipeline-domain/SKILL.md for the vocabulary, then content-pipeline-domain/references/building-a-pipeline.md for the eleven steps.

Designing and porting pipelines

  • content-pipeline-domain/SKILL.md -- the domain skill: the architecture vocabulary and abstraction map for batch pipelines, and the index to the references below. Open it when deciding which shape a new pipeline takes.
  • content-pipeline-domain/references/building-a-pipeline.md -- the eleven-step procedure for a new pipeline: pick shape and unit strategy, wire two-tier freshness, register providers, choose a delivery mode and VCS backend. Open it when standing one up from scratch.
  • content-pipeline-domain/references/porting-a-pipeline.md -- the subsystem-first method for collapsing an existing monolithic LLM-batch tool onto the shared library: inventory against the subpackages, port freshness first, pin the tool's own tests as the equivalence baseline at each step.
  • content-pipeline-domain/references/design-discipline.md -- the opt-in design principles behind the library -- human-always-wins attribution, write-only-on-diff, one-predicate freshness -- and the component that embodies each. Read it when deciding which guardrails to adopt, since none are mandatory.

Wiring worker sessions onto your mount

  • content-pipeline-domain/references/session-recipients.md -- what a session recipient is and how to wire your run onto it: the JSON protocol mount, the adapter fields, the pre-authorized allowlist, the answer fence line, and the reconciliation hook a resumed run needs. Open it when your workers should be Claude sessions.
  • content-pipeline-domain/references/workflow-lane.md -- how the Workflow-tool lane changes that wiring: the agent claims its own unit and gets its fencing token from the claim reply, there is no renewer, and leases are sized once for the whole runtime. The self-claim residual is stated honestly at the end.

Orchestrating a run

  • background-pipeline/SKILL.md -- the four-stage procedure for a background-session dispatcher: prepare, dispatch, batch-boundary status, finalize. Includes the two throughput settings, the report vocabulary, and the rule against ingesting unit content into the supervising session.
  • workflow-pipeline/SKILL.md -- the counterpart procedure for the native Workflow tool, where the top-level session orchestrates every wave. Its four preconditions catch allowlist gaps before any agent is paid for, and re-entry after any interruption is always a fresh invocation.

Executing a single work unit

  • execute-work-unit/SKILL.md -- the procedure for one worker session: the six enumerated invocations, the fence line that proves an answer belongs to its claim, the revision loop on rejected submissions, and why exhaustion means reporting failure rather than fabricating an answer.
