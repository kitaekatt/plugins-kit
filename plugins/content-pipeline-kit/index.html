The content-pipeline-kit plugin package for LLM-in-the-loop batch content pipelines, with plugin and bootstrap metadata, a one-unit worker agent, and a parallel wave workflow.

This is the install and launch surface for the content-pipeline library: the files that make the package a distributable plugin and give its workers somewhere to run. The library itself and the skills the plugin ships each have their own page; what remains here is small on purpose -- a manifest, a bootstrap declaration, one worker agent definition, and one workflow script. The layout follows one split: everything a consumer adopts at install time lives in this directory, and everything that runs per unit runs inside a worker session. The worker and the wave workflow are therefore the whole story of how work gets done here, and both push state mutation behind the consumer's protocol mount.

Where to start

Open bootstrap.json first: its comment block explains the whole install surface -- what the plugin pulls in, what it publishes into the consumer's venv, and which config fields a consumer must supply. If your task is changing worker behavior instead, go straight to agents/pipeline-worker.md.

Routes

  • Install a new consumer: bootstrap.json auto-installs the llm-scripting-kit dependency and publishes the shared library, then the consumer supplies the three fields the file lists -- content root, VCS backend, and LLM backend.
  • Launch a single worker: the consumer's dispatcher opens a background session with the agent-select flag, and agents/pipeline-worker.md takes over from a launch prompt that names the run id, the unit id, and the fencing token.
  • Run a prepared wave: the invoking session computes unit packs in Python, and workflows/run-ready-wave.js fans them out across parallel agent lanes, each claiming, reading, answering, and submitting one unit through the consumer's protocol mount.

What the plugin declares

  • .claude-plugin/plugin.json -- the manifest Claude Code reads on install: name, version, the single dependency on the bootstrap plugin, and keywords.
  • pyproject.toml -- package metadata: the same version, the pyyaml and ruamel.yaml dependencies, and the openai SDK declared here even though live backends reach it through the shared library.

How a consumer installs it

  • bootstrap.json -- auto-installs the llm-scripting-kit dependency, publishes the shared library into the consumer's venv, and lists the config fields a consumer must supply. Open it to debug why an install did not wire up a backend.

The one-unit worker

  • agents/pipeline-worker.md -- the agent definition for a one-unit background session: the unit is reserved before the session starts, the fencing token from the launch prompt is the only authority to submit, and a worker that cannot satisfy the validators runs the fail invocation rather than fabricating an answer.

The parallel wave

  • workflows/run-ready-wave.js -- the native workflow script that runs a prepared wave across parallel agent lanes. It performs no persistence and does no file I/O itself; every change crosses the protocol seam inside an agent, and its returned count is advisory, so the invoking session checks status before acting on it.

Agent guidance

  • CLAUDE.md -- agent-facing guidance; open it when you will change the plugin. It states the seam between what the plugin provides and what a consumer writes, the one-way dependency on llm-scripting-kit, and the process-wide scope of backend selection.
