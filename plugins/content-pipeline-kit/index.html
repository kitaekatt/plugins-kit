Frozen content-pipeline-kit plugin: legacy bootstrap and packaging configuration, with a migration map to llm-kit for the maintained pipeline library, agent, skills, and workflow.

This directory is the frozen shell of the content-pipeline-kit plugin. The pipeline library and the skills that drive it have moved on to llm-kit, so this home now carries what a pointer-only, frozen plugin still needs: its packaging and version, its bootstrap wiring, the public-surface contract with the script that checks a consumer against it, and the worker agent and workflow that older installs still launch by this plugin's name. Read it as a migration map and a compatibility ledger rather than as living code. The heavy machinery is one level down, in the library and the skills.

Where to start

plugins/content-pipeline-kit/README.md is the entry point: it opens with the freeze notice and the migration table, so it tells you in one screen whether you belong here. If your real job is maintaining the pipeline, head for llm-kit instead; this directory exists mainly to say what a legacy consumer may still call.

Migrate to llm-kit

The library splits; everything else moves under the same names. The Python API moves from content_pipeline to llm_kit.pipeline, reorganized into its core, artifacts, runtime, execution, and analysis packages. The four same-named skills (background-pipeline, content-pipeline-domain, execute-work-unit, workflow-pipeline), the pipeline-worker agent, and the run-ready-wave workflow all move to the llm-kit plugin unchanged. New work goes to llm-kit; this directory stays read-only.

Packaging

  • plugins/content-pipeline-kit/pyproject.toml - project name, version 0.37.0, and the dependencies (pyyaml, ruamel.yaml, openai); one of the places the version must stay in lockstep with the library.
  • plugins/content-pipeline-kit/.claude-plugin/plugin.json - the marketplace manifest: the same 0.37.0 version, author, and dependencies. Keep the version here and in plugins/content-pipeline-kit/pyproject.toml equal to the library's version on every bump.

Bootstrap wiring

plugins/content-pipeline-kit/bootstrap.json - what the plugin asks of the host: the 0.120.0 bootstrap floor, publishing the content_pipeline shared lib, the auto-install dependency on llm-scripting-kit (0.61.0), and the three project config fields a consumer must fill: CONTENT_ROOT, VCS_BACKEND, and LLM_BACKEND.

The public surface and its checker

  • plugins/content-pipeline-kit/contract/public-surface.json - the ledger of every public, deprecated, and removed content_pipeline name, each with its status, since-version, and replacement; the source of truth for what a legacy consumer may still call.
  • plugins/content-pipeline-kit/scripts/check_consumer_contract.py - scans a consumer's Python for deprecated or removed names against that ledger and exits 1 on any removed name; run it before trusting a legacy integration. Detection is static, so it sees imports and attribute uses, not dynamic access.

Worker and workflow

  • plugins/content-pipeline-kit/agents/pipeline-worker.md - the one-unit worker agent definition: a background session that claims exactly one unit, runs only the literal invocations it is given, and submits or fails through the consumer's protocol mount.
  • plugins/content-pipeline-kit/workflows/run-ready-wave.js - the native Workflow script that runs one prepared wave through N parallel agent lanes, each claiming, reading, answering, and submitting its own unit through the same protocol seam.

Agent guidance

plugins/content-pipeline-kit/CLAUDE.md - the agent-facing companion to plugins/content-pipeline-kit/README.md: the detailed notes on the adaptive gate, backend selection, cost accounting, and the run-layer pieces. Read it before touching any of the machinery; it is guidance for an agent working in this plugin, not a human reference.
