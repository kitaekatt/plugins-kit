The job-kit plugin packaging and startup path that checks bootstrap provisioning and starts the durable agent-job runner under a provisioned venv.

This directory is the packaging and startup path for the job-kit plugin: the files that decide whether a typed command becomes a running job runner at all. Two launcher shims pick a Python interpreter, a short entry point re-execs the process under the venv that bootstrap provisions, and a vendored guard turns a missing provision into an actionable error instead of a raw import failure. Three manifests pin what that provision must deliver, and a user manual documents the runner once it is up. The runner itself, the job-kit package that executes and records jobs, lives one directory down and has its own page.

Where to start

Open bin/job-kit first: the interpreter preference order and the handoff to the entry point are the entire startup story in one file. When a run dies before it starts, lib/bootstrap_guard.py is the file to read, because it owns the provisioning check and the message you get when provisioning never happened.

Routes

  • Run the runner: bin/job-kit (or bin/job-kit.cmd on Windows) -> lib/job_kit_entrypoint.py -> the package CLI, re-executed under the provisioned venv.
  • A provision never happened: lib/job_kit_entrypoint.py -> the guard in lib/bootstrap_guard.py -> the canonical install-bootstrap message and exit 3.
  • What provisioning must deliver: pyproject.toml -> .claude-plugin/plugin.json -> bootstrap.json.

Startup shims

  • bin/job-kit - The Unix launcher. Prefers the provisioned venv's Python, then a standalone bootstrap interpreter, then PATH, and execs the entry point with your arguments.
  • bin/job-kit.cmd - The Windows twin of the same preference order, with an added guard that rejects the Windows Store python stub in BOOTSTRAP_PYTHON.

Venv entry and bootstrap guard

  • lib/job_kit_entrypoint.py - The process entry: it re-execs under the provisioned venv and only then imports the package CLI. Open it to see why the shims hand off a script rather than a module.
  • lib/bootstrap_guard.py - The vendored, stdlib-only guard. It reads bootstrap's per-plugin log to detect provisioning, emits the canonical not-provisioned message, and performs the venv re-exec with a loop guard; this copy is the canonical source that drift tests compare plugin copies against.

Packaging and provisioning

  • pyproject.toml - The build and distribution: name, Python floor, dependencies, and the job-kit console script. Open it when you change what the wheel installs.
  • .claude-plugin/plugin.json - The marketplace identity: name, version, and the bootstrap dependency. The file a plugin browser reads about this plugin.
  • bootstrap.json - The provisioning contract: the bootstrap version required, the llm-scripting-kit plugin bootstrap must install, and the import set it must verify inside the venv.

User manual

  • README.md - The runner's full manual: commands and exit codes, the job-file format, model selection, command-shaped acceptance, durability, halts, worktrees, and what max_parallel gives up. The first stop for anything past startup.
